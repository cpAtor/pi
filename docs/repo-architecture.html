Diagram 01

Top-level workspace map

The repo is organized as a workspace monorepo with product packages, automation, and contributor policy files kept at the root.

flowchart LR
   root[pi monorepo] --> packages[packages/*]
   root --> workflows[.github/workflows]
   root --> scripts[scripts/]
   root --> docs[docs/ architecture site]
   root --> meta[README + CONTRIBUTING + SECURITY]
   packages --> agent[agent]
   packages --> ai[ai]
   packages --> coding[coding-agent]
   packages --> tui[tui]
   packages --> orchestrator[orchestrator]
  • Root package.json defines npm workspaces across the five published packages plus coding-agent examples.
  • Repository automation sits under .github/workflows and scripts rather than inside individual packages.
  • The new docs site is additive and does not alter package build or runtime code paths.
Diagram 02

Published package dependency spine

The coding agent package is the user-facing entry point and composes the lower-level runtime, model, UI, and orchestration packages.

flowchart LR
   user[User] --> coding[@earendil-works/pi-coding-agent]
   coding --> agent[@earendil-works/pi-agent-core]
   coding --> ai[@earendil-works/pi-ai]
   coding --> tui[@earendil-works/pi-tui]
   orchestrator[@earendil-works/pi-orchestrator] --> coding
   agent --> ai
  • packages/coding-agent/package.json depends on pi-agent-core, pi-ai, and pi-tui.
  • packages/agent/package.json depends on pi-ai for model transport and tool-capable generation.
  • packages/orchestrator/package.json wraps pi-coding-agent for long-lived multi-session RPC supervision.
Diagram 03

CLI startup path

The interactive CLI and RPC entrypoints converge on the same main dispatcher before mode-specific runtime setup happens.

flowchart TD
   cli[cli.ts] --> main[main.ts]
   rpc[rpc-entry.ts] --> main
   main --> parse[parseArgs]
   parse --> mode{Mode}
   mode --> interactive[interactive mode]
   mode --> print[print/json mode]
   mode --> rpcmode[rpc mode]
  • packages/coding-agent/src/cli.ts sets the process title and configures the HTTP dispatcher early.
  • packages/coding-agent/src/main.ts chooses between interactive, print, and RPC execution modes.
  • A single startup path keeps model resolution and session-service wiring consistent across interfaces.
Diagram 04

Session service assembly

Agent sessions are built from a small service graph that isolates authentication, settings, models, resources, and persistence concerns.

flowchart LR
   create[createAgentSessionServices] --> auth[AuthStorage]
   create --> settings[SettingsManager]
   create --> models[ModelRegistry]
   create --> loader[ResourceLoader]
   create --> sessions[SessionManager]
   auth --> runtime[AgentSession]
   settings --> runtime
   models --> runtime
   loader --> runtime
   sessions --> runtime
  • packages/coding-agent/src/core/agent-session-services.ts assembles the runtime and returns initialization diagnostics.
  • AuthStorage and SettingsManager split credentials from user preference management.
  • ModelRegistry and ResourceLoader let the same session runtime consume provider metadata, extensions, skills, and prompt templates.
Diagram 05

Interactive mode composition

The default Pi experience is a layered TUI that combines message history, editor surfaces, and extension-driven overlays around the agent session.

flowchart TD
   shell[Terminal shell] --> tui[TUI runtime]
   tui --> header[header + status]
   tui --> messages[message timeline]
   tui --> editor[input editor]
   tui --> footer[footer metrics]
   extensions[extensions] --> overlays[dialogs + widgets + overlays]
   overlays --> tui
   session[AgentSession] --> tui
  • packages/coding-agent/README.md documents the header, message list, editor, and footer layout of interactive mode.
  • The TUI package provides rendering and editor primitives while coding-agent binds them to session state.
  • Extensions can replace the editor or add custom overlays without forking the main interface.
Diagram 06

Agent turn and event flow

Prompt handling is event-driven: user input enters the session, the core agent loop emits turn and message events, and tool execution feeds back into the same turn.

flowchart LR
   prompt[User prompt] --> session[AgentSession.prompt]
   session --> loop[agentLoop]
   loop --> start[turn_start]
   start --> assistant[assistant message]
   assistant --> tool{Tool calls?}
   tool -->|yes| exec[tool_execution_*]
   exec --> assistant
   tool -->|no| end[turn_end]
   exec --> end
  • packages/agent/README.md describes the streamed event sequence used by the core runtime.
  • Tool execution events interleave with assistant output instead of forming a detached pipeline.
  • This structure is why the TUI, SDK, and RPC mode can all consume the same runtime events.

Built-in tool surface

Pi ships with a deliberately small built-in tool set and then expands capability through extensions and package-level custom tools.

flowchart LR
   llm[Model output] --> router[tool router]
   router --> read[read]
   router --> write[write]
   router --> edit[edit]
   router --> bash[bash]
   router --> custom[custom extension tools]
   custom --> fs[repo + host state]
   bash --> fs
   edit --> fs
   write --> fs
   read --> fs
  • packages/coding-agent/README.md highlights read, write, edit, and bash as the default built-in tool set.
  • packages/coding-agent/src/core/tools/ contains the concrete tool factories and adapters.
  • Custom tools register beside the built-ins instead of replacing the agent loop.
Diagram 08

Extension and resource loading

Runtime customization is file-based and scoped through global and project-local Pi directories.

flowchart TD
   global[~/.pi/agent] --> loader[DefaultResourceLoader]
   project[project .pi/] --> loader
   loader --> ext[extensions]
   loader --> skills[skills]
   loader --> prompts[prompt templates]
   loader --> themes[themes]
   ext --> hooks[event hooks]
   hooks --> session[AgentSession]
  • packages/coding-agent/src/core/resource-loader.ts searches both the user config directory and the project-local .pi tree.
  • Extensions, skills, prompt templates, and themes are all modeled as resources loaded into the same runtime.
  • Reload commands let operators refresh these resources without rebuilding the packages.
Diagram 09

Session persistence and export paths

Sessions are durable JSONL timelines that can be resumed, branched, exported, or shared without changing the in-memory event model.

flowchart LR
   session[Active session] --> save[SessionManager save]
   save --> jsonl[.jsonl session files]
   jsonl --> resume[/resume and /tree]
   jsonl --> branch[/fork and /clone]
   session --> export[/export HTML or JSONL]
   export --> share[/share gist viewer]
  • packages/coding-agent/src/core/session-manager.ts and packages/agent/src/harness/session/jsonl-repo.ts back session storage.
  • The command surface supports resume, branching, cloning, export, import, and sharing from the same persisted history.
  • Export HTML is a presentation layer on top of JSONL rather than a second canonical session format.
Diagram 10

Configuration and environment boundaries

CLI args, config files, environment variables, and discovered provider credentials form a layered configuration stack around each session.

flowchart TD
   cli[CLI arguments] --> resolve[effective settings]
   env[provider env vars] --> resolve
   project[project .pi/settings.json] --> resolve
   global[~/.pi/agent/settings.json] --> resolve
   auth[auth.json + OAuth state] --> resolve
   resolve --> runtime[session runtime]
  • packages/coding-agent/src/config.ts defines config roots such as PI_CODING_AGENT_DIR and session directory overrides.
  • Project-local settings and trust files sit in .pi/ while long-lived user state lives under ~/.pi/agent.
  • Credential storage is intentionally separated from other settings to make trust boundaries easier to reason about.
Diagram 11

Checks, release, and publish pipeline

The repository uses a simple top-level CI path for mainline quality checks and a separate tag-driven release path for binary and npm publication.

flowchart LR
   pr[pull_request] --> ci[CI workflow]
   ci --> install[npm ci --ignore-scripts]
   install --> build[npm run build]
   build --> check[npm run check]
   check --> test[npm test]
   tag[v* tag] --> release[build-binaries workflow]
   release --> binaries[release artifacts]
   release --> npm[npm trusted publish]
  • .github/workflows/ci.yml runs install, build, check, and test on main pushes and pull requests.
  • .github/workflows/build-binaries.yml stages release assets, publishes npm packages through OIDC, and then publishes the GitHub release.
  • Dependency installation in CI uses --ignore-scripts to align with the supply-chain hardening rules in README.md.
Diagram 12

Trust, error, and observability boundaries

Pi treats the launching user account as the main trust boundary, then layers diagnostics, eventing, and timing output around the runtime for visibility.

flowchart LR
   user[local user boundary] --> runtime[Pi runtime]
   runtime --> tools[filesystem + shell tools]
   runtime --> events[EventBus]
   runtime --> diagnostics[startup diagnostics]
   runtime --> timings[printTimings]
   security[SECURITY.md guidance] --> user
   diagnostics --> ui[TUI or CLI surfaces]
   events --> extensions[extension observers]
  • SECURITY.md explicitly states that Pi runs with the permissions of the launching user unless the operator adds a sandbox.
  • AgentSessionServices collects startup diagnostics for extension loading, settings issues, and model discovery problems.
  • Timing output and event-bus hooks provide observability without introducing a separate telemetry backend in the repository.
